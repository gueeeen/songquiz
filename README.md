# 流行音樂猜歌王 SongQuiz

聽 30 秒試聽裡的一段，從九個選項裡選出是哪一首。**純靜態網頁**，雙擊就能玩。

開場先挑三件事：**語種（多選）**、**題數**（5／10／15／20）、**模式**。

- **闖關模式**：關卡跟著你挑的語種長——選 k 個語種就是 k+1 關，一關解鎖一個新語種，
  最後一關全部混合。每關要達到門檻分數才能過，沒過就從第一關重來。
- **競速模式**：一場打完，每題十二秒，答得越快分越高。
- **積分模式（連對加成）**：答對就連莊，倍率一路往上最高 ×5，答錯歸零。
  **不看速度**——只看你能連幾題。

設定會記住，下次打開沿用。題庫湊不出你挑的組合時（例如只選台語卻要每關 20 題），
開打前就會告訴你差幾首，而不是玩到一半沒歌。

題庫每個語種 **700 首可出題 ＋ 500 個誘餌**（誘餌是只當錯誤選項、不會被出題的歌名），
五個語種合計 **3,500 首 ＋ 2,500 誘餌**。歌分兩半：**約 100 首來自 Apple 的播放排行榜**
（每個月重跑就會換新），其餘來自**手挑的 296 位經典歌手**——現場回饋是「歌太新、太難」，
所以流動性只留在榜單那一層。

---

## 玩

雙擊 **`開啟網站.cmd`**，或直接雙擊 `web\index.html`。

沒有伺服器、沒有安裝步驟、沒有打包工具。整個 `web\` 資料夾丟到任何靜態空間
（GitHub Pages 之類）也能直接跑。

**和朋友在同一個 Wi-Fi 搶答**：雙擊 **`區域網路開房.cmd`**，它會印出這台電腦的
區域網路網址（像 `http://192.168.0.17:5000/room.html`）——叫朋友用手機瀏覽器打開它，
一個人建房、把四位房號念出來，其他人輸入房號就進來了。
**不用註冊、不用金鑰、不用改任何設定**（網頁就是這台電腦送出去的，
所以它自己就知道中繼在哪裡）。第一次跑要在 Windows 防火牆提示按「允許存取」。
朋友不在同一個場地才需要另外設定 Supabase，步驟見 `多人房間.md`。

個人最佳成績記在瀏覽器的 localStorage 裡，按「模式＋題數＋語種組合」各記一筆
（闖關另外記最遠關卡）——5 題的積分和 20 題的闖關不是同一件事，混在一起比沒有意義。
換瀏覽器或清掉網站資料就會歸零——這是刻意的，沒有伺服器就沒有跨裝置的成績。

## 重建題庫

雙擊 **`重建題庫.cmd`**（需要網路，約三到五分鐘）。

### 歌是怎麼挑的

現場玩過之後改過一輪：回饋是「歌太新、太難」，所以**榜單只留來當流動性，其餘換成
手挑的經典歌手**。

**三層，按 Fame 由小到大（越小越有名，難度分級照這個切）：**

| | 來源 | 每語種幾首 | 換不換 |
|---|---|---|---|
| ① | 榜上直收的歌 | 約 100 | **每月換** ← 流動性只來自這裡 |
| ② | 手挑經典歌手的歌（每人 15 首） | 填到 700 | 名單固定，歌會微調 |
| ③ | 榜單歌手的其他歌（每人 5 首） | 補尾巴 | 每月換 |
| ④ | 補深度管道的歌 | 40 | 每月換，**算「困難」** |

**經典名單排在榜單歌手前面**：額度先到先得，榜單歌手的歌正是最新的那些。

**經典 15 首、榜單 5 首**是刻意不同的：榜上多半是新人，歌單薄，第 6 首之後就是專輯
冷門歌；經典歌手的前十幾首全是代表作（伍佰第 16～24 首還是牽掛、夜照亮了夜、白鴿）。

#### 用 artistId 撈歌，不用名字

`Artists.cs` 的名單帶 artistId，取歌走 `lookup?id=…&entity=song`。**用名字搜會拿錯
人，而且是靜靜地錯**：

* 搜「LiSA」Apple 先給你小野麗莎（bossa nova）。那個錯誤真的上線過——舊題庫的日語裡
  有 6 首 Take Me Home Country Roads、Fly Me To The Moon 這種歌。
* 搜「Queen」撈不到 Queen 本人（一首叫 Queen 的日文歌排在前面），搜「Perfume」是 0 首。
* 同一個人兩個名字：RSS 榜單叫「BTS」、Search 叫「防彈少年團」。

榜單那半不用多打請求——RSS 的 `im:artist.attributes.href` 裡就有 id。

| 管道 | 語種 | 角色 |
|---|---|---|
| tw/1253 華語流行樂 | 華語 | 流動性 |
| tw/1254 台灣流行樂 | 台語 | 流動性 |
| tw/51 ＋ us/51 ＋ jp/51 K-Pop | 韓語 | 流動性（三家聯集，Apple 沒有全球榜）|
| tw/1252 韓國流行 | 韓語 | **補深度**（獨立與抒情的長尾）|
| tw/27 J-Pop | 日語 | 流動性 |
| jp/27 J-Pop | 日語 | **補深度**（傑尼斯與偶像團，台灣人多半不認得）|
| us/14 ＋ gb/14 Pop | 西洋 | 流動性 |
| tw/1251 粵語流行 | 粵語 | 管道備好了，但**不寫進題庫**（見 `Languages.InBank`）|

踩過的坑都寫在 `Charts.cs` 的註解裡，包括「韓語的曲風 id 是 51 不是 1252」
（1252 六個商店試過都只有長尾，一個大團都沒有）。

#### 難度與出題比例

題庫裡每語種切成 **簡單 40%／中等 30%／困難 30%**（`Difficulty.cs`）。

**出題比例是每個語種各一組**（`rules.js` 的 `DIFFICULTY_MIX_BY_LANGUAGE`）：

| 語種 | 出題 | 理由 |
|---|---|---|
| 華語／台語／西洋 | **純隨機**，不分難度 | 整池都是手挑的經典，tier 想表達的「認得出來」已經由選歌保證了 |
| 日語 | 簡單 90%／困難 10% | 簡單＝台灣 J-Pop 榜＋動漫歌手；困難＝日本本地榜那 40 首 |
| 韓語 | 簡單 60%／中等 30%／困難 10% | 老團（少女時代、SHINee）和當紅團認得出來的程度差距大，分級還有價值 |

選多個語種的時候**每個語種機會均等**——原本是從混合的池子直接抽，等於按題庫大小加權。

#### 年代覆蓋

Apple 的免費端點**沒有年代排行榜**（實測 `decade=2000` 是被靜默忽略的，回傳和當期榜
一字不差）。年代覆蓋是從 `releaseDate` 看的，而它是順便來的：Search／lookup 的排序
本來就按人氣，老歌手的前十幾首就是他的代表作。實測分佈：

    華語  1970s 1、1980s 10、1990s 56、2000s 192、2010s 264、2020s 79
    台語  1970s 8、1980s 34、1990s 130、2000s 89、2010s 198、2020s 100
    西洋  1970s 4、1980s 10、1990s 48、2000s 103、2010s 342、2020s 93
    日語  1990s 8、2000s 43、2010s 203、2020s 308
    韓語  2000s 31、2010s 305、2020s 224

每次重建都會印出來——標籤會騙人（我可能記錯某個歌手的年代），`releaseDate` 不會。

### 每個月重跑

雙擊 `重建題庫.cmd` 就好。榜會換人，所以每個月跑一次**榜單那 100 首**就會跟著換新。
經典那部分不會變——那是刻意的，它們就是拿來當定錨的。

**不是直接覆蓋，是合併。** 預設 `--carry 0.30`：每語種 700 個名額裡，
490 個給這次撈到的，210 個留給「上一版還在、這次沒撈到」的歌。兩個理由：

一、**一條管道壞掉就少一個語種。** 榜單是外部服務。重跑時剛好連不上，
直接覆蓋會產出一份缺語種的題庫，而且是靜悄悄的。有合併就會自動用上一版補滿，
而且畫面上會印出「這個月 N 首 ＋ 上一版留下 M 首」——M 異常大就是管道出問題了。

二、**換血要平順。** 上個月紅、這個月掉榜的歌，玩家未必忘了。
整批換掉會讓「上個月才猜過的歌這個月完全不見」。

**改了挑歌規則的那一次要用 `--carry 0`。** 合併會把上一版的歌拉回來，而上一版是
用舊規則建的——實測踩過一次：把「每人取 15 首」改成「前 5 首」之後，台語只撈到
240 首，合併就從上一版補了 160 首回來湊滿，而那 160 首正是要避開的專輯冷門歌。
這一次的經典改版同樣是 `--carry 0` 建的。規則沒改的月度重跑才適合用預設的 0.30。

想讓題庫**長大**而不只是換血，就把 `--tracks` 調高（每語種 +100 首大約讓
`bank.js` 多 18 KB，gzip 後 8 KB）。

**`Artists.cs` 那份名單現在是主力，不是備援。** 這件事反過來了：舊版的榜單就填滿了
上限，手打名單一位都沒被問到、貢獻 0 首；現在經典那一層排在榜單**前面**，700 個名額
裡有 600 個是它的。要加歌手就改 `names.json` 再跑 `resolve.mjs`（那一支的檔頭寫了
怎麼跑），不要直接手寫 artistId。

### 難度分級

題庫裡每一首歌都貼了難度（0 簡單／1 中等／2 困難），出題時照比例挑。

**怎麼分的**：每首歌有一個 `Fame` 分數（越小越有名），由兩個排名合成：

* **歌手有多紅** —— 他在排行榜上的名次。那是真的播放排行。
* **這首歌在他的歌裡有多紅** —— Search API 回傳的順序。實測是知名度排序
  （周杰倫回「晴天、七里香…」，Taylor Swift 回「Cruel Summer、Love Story…」）。

合成方式讓歌手的名次主導、歌的順序當細分 —— 一線歌手的第五首，多數人還是比
三線歌手的第一首熟。然後**每個語種各自**依 `Fame` 排序，前 40% 簡單、
接下來 30% 中等、最後 30% 困難。

各自切很重要：混著切的話，歌手普遍比較紅的語種會把另一個語種整個推到「困難」，
而玩家選的是語種，難度必須在語種內部相對。

**沒有播放次數這種絕對數字可用。** Apple 不給，Spotify 只給 0～100 的相對熱度
而且要註冊金鑰。所以這裡的「難度」是相對的：第 1 名和第 200 名都叫「簡單」，
它的意思是「在這個語種裡算好認的一半」。

**出題比例**每個語種各一組，在 `web/js/rules.js` 的 `DIFFICULTY_MIX_BY_LANGUAGE`
（哪個語種是哪一組，見上面「難度與出題比例」）。那和題庫的比例是兩件事：
題庫裡簡單佔 40%，日語卻有九成的題目從那 40% 出，所以有名的歌會被重複用到——
那正是要的。原本九個選項從整個語種隨機抽，一首冷門歌和一首國民歌中獎率一樣，
玩起來就是「大部分題目沒聽過」。

**華語、台語、西洋現在不看難度，純隨機。** 整池都是手挑的經典，tier 想表達的
「認得出來」已經由選歌保證了，再分一層只是把同一批歌裡最紅的那些再放大一次。
日語和韓語留著分級，理由寫在上面那張表裡。

### 參數

| 參數 | 預設 | 說明 |
|---|---|---|
| `--per-artist` | 5 | 榜單上的演出者取幾首進題庫（前幾首才是有名的）|
| `--classic-per-artist` | 15 | 經典名單的歌手取幾首——老歌手的前十幾首全是代表作 |
| `--decoys-per-artist` | 14 | 同一位再取幾首當誘餌 |
| `--tracks` | 700 | 每個語種的題庫上限 |
| `--decoys` | 500 | 每個語種的誘餌上限 |
| `--chart-limit` | 100 | 榜單一次要幾名（Apple 實測上限 100） |
| `--carry` | 0.30 | 上限裡留多少比例給上一版的歌；**改了規則要傳 0** |
| `--chart-songs` | 100 | 每個語種直接從榜上收幾首（流動性全部來自這一層）|
| `--depth-songs` | 40 | 補深度的管道另外收幾首（日本本地榜、韓語 1252），算「困難」|
| `--classics` | 空 | 經典種子檔。**預設關掉**：舊的 `經典歌單.js` 日語那半有 13 首是搜錯人搜來的 |
| `--country` | TW | Search／lookup 的商店地區 |
| `--delay` | 800 | 兩次請求間隔（毫秒）——榜單兩段式之後請求數變三四倍，400 會一直吃到 Apple 的限流 |
| `--out` | `web\data\bank.js` | 輸出位置 |

### 關於那個檔

`bank.js` **有進版控**——純靜態站的話，那個檔就是網站的內容本體，
少了它 clone 下來沒裝 .NET 的人就沒得玩。

它存成陣列再由檔案自己展開，不是一般的物件 JSON：題庫是每個玩家一進站就要下載的東西，
而現場多半是手機網路。物件形式會把五個鍵名在每一首歌重複一次、網址的共同前後綴也是，
兩千首就差好幾百 KB。展開出來的 `window.SONG_BANK` 形狀和以前完全一樣，網頁端一行都不用改。

## 測試

測試分兩層：無頭 Edge 那一層跑得快、不用網路；Playwright 那一層真的開瀏覽器、
真的連 Apple 和 Supabase。

### 第一層：無頭 Edge

**遊戲規則**（96 項）：打開 `web\tests.html`，最上面會顯示 `RESULT PASS 96/96`。

**版面**（55 項）：打開 `web\layout-tests.html`。它把 `index.html` 分別用 390px 和
1200px 的寬度載進兩個 iframe，量實際排出來的尺寸——開始鈕有沒有釘在底部、出處會不會
被它蓋住、九宮格在桌機上是不是還像格子、日夜兩種主題的對比夠不夠（連「卡片對頁面」
和「邊框對卡片」都量，只量文字會漏掉「字很清楚但整頁糊成一片」那種壞法）。
這些都是宣告寫對、卻被別條規則蓋掉就看不出來的東西，所以一律量
`getBoundingClientRect` 和 `getComputedStyle`，不看 CSS 原始碼。

**整場**（14 項）：打開 `web\playthrough.html`。它把一整場十題從頭打到完，
看會不會走到結算頁，以及「再來一場」有沒有真的把上一場洗掉。
前兩份都不會真的跑完一局，而「打到第七題就卡住」這種錯，只有真的打完才看得到。

測試不依賴 Node，也沒有測試框架：三頁都是自己寫的極小跑法，打開就跑完。
要無頭跑（CI 也能用同一條）：

```
msedge --headless=new --disable-gpu --virtual-time-budget=5000 --dump-dom "file:///…/web/tests.html"

msedge --headless=new --disable-gpu --allow-file-access-from-files ^
       --virtual-time-budget=20000 --dump-dom "file:///…/web/layout-tests.html"

msedge --headless=new --disable-gpu --allow-file-access-from-files ^
       --autoplay-policy=no-user-gesture-required ^
       --virtual-time-budget=120000 --dump-dom "file:///…/web/playthrough.html"
```

後兩條一定要加 `--allow-file-access-from-files`：從 `file://` 開的頁面，
iframe 算跨來源，沒有這個旗標就讀不到裡面的文件，測試會全部掛在「讀得到被測頁面」。

**題庫產生器**（44 項，歌名清洗、題庫檔的格式契約、每月合併的往返、三層疊法與難度分級）：`dotnet test`。
其中一條是跨語言的：C# 的 `Languages.InBank` 必須和 `webjsules.js` 的 `LANGUAGES` 一致——
那條線兩邊不同步的話，不是白下載一整個語種，就是首頁多一顆選了會開不了場的膠囊。

### 第二層：Playwright（`tools\qa`）

第一層有一整類東西驗不到：無頭 Edge 沒有音效裝置，也連不到 Apple，
所以測試裡的音訊一律走「放不出來」那條路。第二層補的就是這些——
iPhone/WebKit、Android/Chromium、桌機三組，各跑真的一場：

* **真的發得出聲音嗎**：`currentTime` 有沒有在前進。
* **慢網路下會不會卡**：用 Chrome DevTools Protocol 把頻寬壓到 2 Mbps，
  量每一題從「畫面出現」到「音樂響起」之間的毫秒數。
  這一條抓到過兩個真正的缺陷：並行預載會把正在播的那一首餓死；
  以及 `<audio>` 的 `canplaythrough` 根本是估的——限速下它 585 毫秒就回報
  「可以一路播完」，那時候只抓到 1.1 秒（整首 30 秒）。
* **兩台機器看到同一題嗎**：兩個瀏覽器 context 各開一條 Supabase 連線，
  比對九個選項逐字相同、順序相同。

```
cd tools\qa
npm install && npx playwright install chromium webkit   :: 第一次
npm test
```

預設測的是**工作目錄裡的版本**（`serve.js` 把 `web/` 端成 HTTP）。
要驗線上：`set QA_BASE_URL=https://gueeeen.github.io/songquiz/ && npm test`。
一輪正常是 37 通過、11 跳過（限速與多人那幾條只有 Chromium；量時間的那幾條在
WebKit 上跳過——它沒有音效裝置）。
細節與「WebKit 起不來怎麼辦」在 `tools/qa/README.md`。

### 還是要拿手機做的

Playwright 的 WebKit **不是** iOS Safari：真機的自動播放規則更嚴，還有鎖屏、
切 App、來電中斷，以及兩台真的在不同網路上的裝置。
清單在 [QA清單.md](QA清單.md)，要拿著手機一項一項做。

播放的每一段都是 **Apple Music 官方的 30 秒試聽**，透過 Apple 公開的
[iTunes Search API](https://performance-partners.apple.com/search-api) 取得網址，
播放時**由 Apple 的伺服器直接串流到玩家的瀏覽器**。

- 本專案**不下載、不轉存、不代理、不快取**任何音訊；`web/data/bank.js` 裡存的
  只有歌名、演出者與 Apple 的試聽網址。
- **所有歌曲的著作權屬於原權利人**（詞曲作者、表演者、唱片公司）。
- 本專案與 Apple Inc. 沒有任何關係，也未經其背書。Apple、Apple Music、iTunes
  是 Apple Inc. 的商標。
